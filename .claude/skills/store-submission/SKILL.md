# ストアのコンソールを一緒に進める

発表者が画面を見ていて、こちらは**スクリーンショットでしか見えない**状況のための進め方。

## 鉄則: 一度に1ステップだけ

**先の手順をまとめて並べないこと。** 実際の画面はこちらの想像と必ず少しずれていて、
まとめて書くと「若干違う」説明になり、相手がどれを読めばいいのか分からなくなる。

1. **いま見えている画面でやることだけ**を言う
2. 終わったら次の画面を見せてもらう
3. 実際に見えているものに合わせて、次の1手を言う

例外は、**その画面の中で完結する複数項目**（1つのフォームの各欄など）。
これは1ステップとして一度に書いてよい。

## 貼る文面は、その場で出す

長い英文（capability の正当性説明など）は「ドキュメントを見て」で済ませず、
**そのメッセージの中にコードブロックで出す**。コンソールと別ファイルを
行き来させない。正はリポジトリのドキュメント側に置き、出すときは
`awk` / `sed` で抜き出して貼る（手で書き写すと食い違う）。

## 画面を見たら必ず確かめること

- **出ている警告がエラーなのか想定内なのか**を最初に言う。
  例: restricted capability の「approval が要る」は**エラーではない**（理由を書けば通る）
- **状態バッジ**（未開始 / 未完了 / 完了）を読んで、次にどこを押すかを決める
- スクリーンショットの**寸法や文字も読む**。審査で弾かれるのはたいていそこ

## このリポジトリの正

| 配布先 | ドキュメント |
|---|---|
| Microsoft Store | `docs/ms-store-listing.md` |
| App Store | `docs/app-store-listing.md` |
| Windows 版の実装と実測 | `docs/windows-spike.md` |
| MSIX の作り方 | `scripts/build-msix.ps1` のヘッダ |
| スクリーンショット撮影 | `scripts/take-screenshot.ps1` |

**答えはまずここを読んでから出す。** 記入済みの値（Identity Name、Publisher、
URL 一式）も、貼る文面も、審査で聞かれることへの回答案も揃えてある。
推測で答えない — ストアの値は不一致だと提出が弾かれる。

## 進めながらドキュメントを育てる

画面で分かった新しいこと（入口の URL、引っかかった検証エラー、申告の場所）は、
**その場で該当ドキュメントに書き戻してコミットする**。次の申請と、バージョンアップの
たびの再提出で同じ画面を何度も通るため。
