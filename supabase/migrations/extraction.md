# KPIシート準拠の集計定義（最優先）
以下は今回提示されたPostgreSQL集計SQLの意味を正とする。以前の「3週間以内入会率」SQLは誤提示だったため、定義・出力とも完全に廃止する。昨日のレポート値もKPI比較値として再利用しない。

## 集計期間
- 日時はAsia/Tokyoとして扱い、開始・終了日時を必ず表示する。
- **S3 Tablesの日時列（`ins_ts` / `upd_ts` / `agency_viewed_ts` / `schedule_ts` 等）はUTCで格納されている。SQLの期間条件はJSTの境界をUTCへ変換してから指定する。** 例: JST `2026-08-31 00:00:00`〜`2026-09-07 00:00:00` は、S3上ではUTC `2026-08-30 15:00:00`以上〜`2026-09-06 15:00:00`未満。
- 期間条件は必ず半開区間 `>= 開始UTC AND < 翌期間開始UTC` とする。JSTの日付文字列を未変換のままS3へ渡したり、終了日の`23:59:59`を使ったりしない。
- KPI表にはJST期間と、実際にSQLへ渡したUTC期間を併記する。初回集計では未変換JST境界の件数も検算し、差が0件でない場合はUTC変換後の件数だけを採用する。
- KPIシートの対象期間を取得できる場合は、その期間をそのまま使う。
- 対象期間が不明な場合だけ、完了した直前の月曜00:00:00〜日曜23:59:59の7暦日を使う。
- 提示SQLの例 `2026-06-07`〜`2026-06-14 23:59:59` は両端を含めると8暦日である。これを通常の7日週として流用しない。
- CV数は見込み客登録日 `t_potential_customer.ins_ts`、入会数は会員登録日 `t_member_all.ins_ts` に期間条件を適用する。両者は同一人物コホートではない。

## S3差分追加テーブルでの数え方
参照SQLはPostgreSQL上の行数を数えるが、S3は更新版を日次追記する。生の `COUNT(*)` は将来のsnapshot追加で膨張するため、S3の主結果は各テーブルを主キーごとの最新行へ絞ってから条件を適用する。

- 見込み客は `potential_customer_id`、会員は `member_id` の最新行を使う。実在する主キーと最新版判定列は実データで再確認する。
- 結合後に `COUNT(DISTINCT ...)` へ置き換えて黙って意味を変えず、どの行を最新版として除外したかを記録する。
- 初回snapshotだけの期間で生行数も安全に確認できる場合は、参照SQL相当の生行数と最新版行数を併記する。
- S3にはpublic/history/garbageの由来列がないため、PostgreSQL参照SQLとの完全一致を保証しない。差分があれば、期間、版重複、PII依存加算、由来不明の順に説明する。


### `t_marriage_episode` の件数ルール
- 主キーは `marriage_episode_id`。S3は更新行を日次差分として追記するため、同じIDの更新版が複数snapshotに存在し得る。
- 2026-09-09確認時点では、6,802行・6,791一意ID・重複分11行。重複11 IDはすべて2 snapshot・2種類の `upd_ts` を持つ更新版で、同一版の二重取込ではない。この数値はデータ健全性の参考値であり、毎回Step 0で再計測する。
- **登録されたエピソードの一意件数**だけを数える場合は `COUNT(DISTINCT marriage_episode_id)` を使う。週次・月次の新規登録件数は、JST境界をUTCへ変換した半開区間で `ins_ts` を絞り、`COUNT(DISTINCT marriage_episode_id)` とする。
- **現在公開中、下書き中、削除済み等の最新状態を条件にする件数**は、先に対象IDの全更新版から `ROW_NUMBER() OVER (PARTITION BY marriage_episode_id ORDER BY upd_ts DESC, snapshot_date DESC)` の `rn = 1` へ絞り、その後で `public_flag`、`draft_flag`、`delete_ts` 等の可変条件を適用して `COUNT(*)` する。可変条件を最新版判定より先に適用しない。
- `COUNT(DISTINCT marriage_episode_id)`だけでは古い版の `public_flag` 等を除外できないため、状態別件数には使用しない。
- `snapshot_date = MAX(snapshot_date)`だけで最新状態を取得しない。各 `snapshot_date` は全件snapshotではなくその日の差分取込であり、最大日だけに絞ると当日追加・更新された行しか残らない。
- 検算として、生の `COUNT(*)`、`COUNT(DISTINCT marriage_episode_id)`、最新版行数、重複ID数を併記する。件数差があれば、更新版追記による差か、同一 `marriage_episode_id`・同一 `upd_ts` の二重取込かを分けて報告する。

## `statuses_id` を扱うクエリでは特に必須

`statuses_id` は「未対応→連絡待ち→…→入会/NG」と更新で変化する列なので、
**同一見込み客について複数の `statuses_id` が同時にテーブルに存在する。**
素朴に `GROUP BY statuses_id` で数えると、1人が複数ステータスに二重計上される。

**最新状態を見る場合は必ず主キーごとに `upd_ts` 最大の行へ絞れ。**

```sql
WITH latest AS (
  SELECT *,
         ROW_NUMBER() OVER (
           PARTITION BY <主キー列> ORDER BY upd_ts DESC
         ) AS rn
  FROM t_potential_customer_informations
)
SELECT statuses_id, COUNT(*) AS n
FROM latest
WHERE rn = 1          -- ← これを落とすと二重計上
GROUP BY statuses_id
```

同じ扱いが必要な列（すべて更新で変化する）:
`statuses_id` / `agency_viewed_ts` / `potential_rate_kbn` / `memo` /
`t_potential_customer.agency_id` / `t_member_all.withdraw_kbn` /
`t_agency_info` の掲載・料金・報酬関連すべて

`PARTITION BY` に使う主キー列名は必ず `list_tables` / 実クエリで確認してから使う。

# ドメイン制約（これを守らないと数字が必ず間違う。厳守）

## データ基盤側の制約
- 全テーブルに `snapshot_date`（date）が付与されている。連携は**日次バッチ**。
- **`public` スキーマと `garbage` スキーマ（論理削除済）が UNION ALL 済みで、両者を区別するカラムは無い。**
- **データ保持は初回バックフィル＝直近1年**。それより古い期間の傾向は語るな（語る場合は「データ範囲外」と明記）。
- 氏名系カラムはPII除外のため**存在しない**（`family_kj` 等）。個人特定はするな。
- 件数は必ず **`COUNT(DISTINCT <主キー>)`**、または上記 `rn = 1` で絞った上での `COUNT(*)` を使う。
  生の `COUNT(*)` は複数バージョンを数えてしまう。

## 費用制約（egress）
MCP はローカルからIcebergを直接読むため、**転送量がそのまま課金される**（約 $0.114/GB）。
- **`SELECT *` を LIMIT なしで投げるな。** 必要な列だけを明示的に指定せよ。
- 集計は可能な限りSQL側で完結させ、生データをローカルに引き出すな。

## 見込み客ドメインの制約（最重要）
- **親子構造**: `t_potential_customer` は
  - **親レコード** = ユーザーのフォーム送信そのもの（`parent_pc_id IS NULL`）
  - **子レコード** = HQが相談所へ送客した単位（`parent_pc_id` に親ID、`agency_id` が入る）
  - **純粋なWeb由来CV** = `parent_pc_id IS NULL AND ins_id IS NULL`（`ins_id NOT NULL` はスタッフ手入力）
- **utm / gclid / yclid / form_sender / link_before_conversion は親レコードにしか入らない**（少なくとも過去分）。
  相談所別に流入経路を見るときは、子レコードから `parent_pc_id` で親へ JOIN して属性を復元せよ。
- **入会判定は `t_member_all.potential_customer_id`（見込み客への外部キー）を第一とせよ。**
  - 入会日時 = `t_member_all.ins_ts`
  - `visible_flag IS TRUE` のみ有効（false はデモ/テスト会員）
  - 1見込み客 : 最大1会員
  - `statuses_id = 7`（入会）は**クロスチェック用**。`rn = 1` で絞らないと信用できないため主判定に使うな。
- **ステータス**は `t_potential_customer_informations.statuses_id` →
  `1:未対応 / 2:連絡待ち / 3:面談待ち / 4:結果待ち / 5:保留 / 6:NG判定 / 7:入会`
  （+相談所独自ステータスが最大3件。`all_agency_available_flag` で共通/独自を判別）
  ※このIDはシード順依存。**実データで `t_potential_customer_statuses` を必ず突き合わせて確認せよ。**
- **`informations` 行が存在しないCVがある**（資料請求のみのCV等では生成されない）。
  → `t_potential_customer` を起点に **必ず LEFT JOIN**。INNER JOIN すると歩留まりが過大評価される。
- **`agency_viewed_ts`（既読日時）は「相談所がそのCVを見たか」の最良シグナル**。NULL = 未閲覧。
  ※更新で埋まる列なので `rn = 1` 必須。
- **相談所の実アクションは `t_potential_customer_interview_management`**（1見込み客に複数行）。
  `schedule_ts`（予定）、`interview_log`（記録）、`category_kbn`（28302:面談 / 28303:電話 / 28304:メール）、
  `interview_format_kbn`（24901:対面 / 24902:オンライン）
  ※このテーブルは「1見込み客に複数アクション」＋「1アクションに複数バージョン」の二重構造。
    アクション数を数えるときは先に `rn = 1` で最新版へ潰してから数えよ。
- **`t_potential_customer_reasons_for_not_joining` は現行フローではほぼ書かれていない legacy テーブル**。
  必ず件数を先に確認し、n が小さければ「参考値」と明示するか、結論の根拠に使うな。
  現行のNG判定は `statuses_id = 6` 側で見ること。
- `t_agency_info` は**予約版（下書き）行を含む**。現在の公開情報は `reserve_flag IS FALSE` かつ `rn = 1`。
- テスト相談所は除外すること（`agency_id` の異常値・件数外れ値から判断し、除外した対象を明記せよ）。

# 分析期間と多角的な仮説設計
単週比較だけで結論を出さず、次の時間軸を併用する。

- 週次: 月曜00:00:00〜日曜23:59:59。直近の完了週を基準週とし、最低13週を並べて短期変化・外れ値・4週移動平均を見る。
- 月次: 直近12か月を暦月ごとに分割取得し、中期トレンド・季節性・問い合わせ種別構成を確認する。
- CVコホート: CV登録週を起点に、1週間・3週間・6週間後の送客、既読、面談予定、対応ログ、入会を追う。比較時は同じ観測期間（7日・21日・42日）が完了したコホートだけを使う。
- 相談所運用: 直近3か月を基本とし、送客数が少ない相談所は個別順位を断定せず群比較にまとめる。
- KPIシート集計: CV登録日基準のCV数と会員登録日基準の入会数を別々に集計し、CVコホート率と混同しない。

毎回、少なくとも次の視点から仮説を立て、データで支持・否定・判定不能を明記する。

1. **CV獲得**: `form_sender`、`utm_source`、`utm_medium`、`utm_campaign`、`link_before_conversion`、問い合わせ種別、曜日、地域別にCV量と構成比を分析する。サイト訪問・PV・広告imp/clickデータがない場合、サイト訪問→CV率や広告効率は算出せず、必要なログを提示する。
2. **問い合わせ内容・ユーザーニーズ**: `inquiry_kbn`、`consultation_method_kbn`、希望日時入力状況、希望エリア、性別・年代など匿名化された属性、`bk` / `hq_memo_cont` のキーワード件数を集計する。自由記述は個票を出力せず、30件以上の集約カテゴリだけを使う。料金、オンライン、対面、エリア、年齢、再婚、子ども、活動時期、不安などの仮説カテゴリを作り、重複回答として集計する。
3. **CVの質**: 流入元・問い合わせ内容別に、同じ観測期間が完了したCVの送客率、既読率、面談予定率、対応ログ率、入会率を比較する。単週のCV数と同週入会数の比だけで質を断定しない。
4. **送客設計**: 親CVから子レコードが何件作られたか、送客先数、送客先の分散、相談所属性との適合を確認する。無料CSLなど直接相談所へ入る経路と、紹介・資料請求など親子構造を持つ経路を分ける。
5. **相談所オペレーション**: 既読速度、面談予定、対応ログ、アクション種別・回数、放置率と入会の関連を見る。action行の存在が自動生成等で全件に付く場合は指標にせず、ログ・予定・業務イベント時刻を使う。
6. **期待値ギャップ**: 相談方法、エリア、希望日時と、相談所のオンライン対応・店舗・対応地域・料金・無料相談条件を照合する。区分値が未確認なら推測で一致判定しない。
7. **ユーザーが入会しない理由**: 現行データで理由が取得できるかを先に確認する。legacyテーブルの更新が止まっている場合、現在の理由として使わず、計測追加を企画へ含める。
8. **Positive Deviance**: 十分な送客数を持つ上位相談所と下位相談所を比較し、既読だけでなく面談予定率・ログ率・入会率・相談所属性の違いを見る。
9. **データ可視性**: 外部Excel等の運用可能性を、レコード欠落ではなく面談予定・ログ・見込み度・理由の欠損として定量化する。

# 高速・省メモリのクエリ設計
- PyIceberg/Daftでは、この環境の `CAST('YYYY-MM-DD' AS timestamp)` がNULLになることを確認済み。期間絞り込みは、JST境界をUTCへ変換した完全な日時文字列を使い、`CAST(ins_ts AS string) >= 'YYYY-MM-DD HH:MM:SS' AND CAST(ins_ts AS string) < 'YYYY-MM-DD HH:MM:SS'` とする。週次・月次ともUTC変換を省略しない。
- 最初に単一テーブルの期間別・カテゴリ別集計を取り、仮説を絞ってから結合する。
- 大規模JOINは、各テーブルを対象期間と必要列へ先に絞る。親ID・子ID・相談所ID単位へ事前集計した小さなCTE同士だけを結合する。
- `OR` JOINは禁止。親自身と子を扱う場合は別集計に分け、ローカルで加算するか、等価キーへ正規化する。
- 最新版判定が必要な場合も、期間条件を先に適用してから `ROW_NUMBER()` を使う。条件が変わらない指標は生行数と `COUNT(DISTINCT 主キー)` を検算し、一致する場合に限りDISTINCT集計で高速化する。
- 13週・12か月は1期間ずつ逐次取得し、各クエリ結果を直ちに保存する。成功済みの期間を再取得しない。
- 自由記述や個票を大量取得しない。SQL側でNULL率・キーワード件数・カテゴリ件数へ集約する。
- 30秒を超える結合は停止し、単一テーブルまたは親・子・会員・アクション別の小集計へ分割する。

# 分析ステップ（各Stepで必ず自分でSQLを発行し、実数値を根拠にせよ）

## Step 0: データ健全性の確認（これを飛ばすな）
- 各テーブルの件数、`snapshot_date` の最小/最大、`ins_ts`（登録日）と`upd_ts`（更新日）のカバー期間
- **各テーブルで `COUNT(*)` と `COUNT(DISTINCT <主キー>)` を比較し、重複バージョンの規模を把握する**
  （初回投入直後は差分がゼロまたは小さくても正常。`snapshot_date`は取込日、`ins_ts`は元データの登録日として区別する）
- 親/子レコードの比率、`informations` 行の付与率、`interview_management` 行の付与率
- utm の欠損率（親 / 子それぞれ）
- **`ins_ts` が直近1年をカバーしているか**を月別件数で確認する。初回投入日が本日でも、過去の`ins_ts`を持つ行は登録月の分析対象に含める
- **この Step の結果を踏まえて、以降どの指標が信頼でき、どれが語れないかを先に確定させること。**

## Step 1: ファネルの定量化（ボトルネックの発見）
まずKPIシート比較用の期間内CV数・期間内入会数を出す。その後、13週の週次推移、12か月の月次推移、観測期間が完了したCVコホートで以下の各段の実数と転換率を出す。
```
CV（親, Web由来） → 送客（子レコード生成） → 既読（agency_viewed_ts） →
初回アクション（interview_management 初回行） → 面談実施 → 入会（t_member_all）
```
- **どの段の転換率が、いつから、どれだけ落ちたのか**を特定する
- 各段のリードタイム中央値を、ステータス遷移履歴ではなく次の業務イベント日時から算出する
  - CV→既読: 親CVの `t_potential_customer.ins_ts` → 対象見込み客の `agency_viewed_ts`
  - CV→初回アクション: 親CVの `ins_ts` → 同一親CV配下にある `t_potential_customer_interview_management.ins_ts` の最小値
  - 既読→初回アクション: `agency_viewed_ts` → アクション `ins_ts` の最小値
  - 初回アクション→入会: アクション `ins_ts` の最小値 → 有効会員の `t_member_all.ins_ts`
  - 面談予定までの日数を扱う場合: 親CVの `ins_ts` → 面談カテゴリ（28302）の `schedule_ts`
  - 各区間で日時欠損数、負の時間差、対象n数を併記し、異常値を除外した条件を明示する
- 「CV増加分がどの段で消えているか」を、CV増加前後の期間比較で示す

## Step 2: 多角的な要因分解（以下すべての軸で切れ）
1. **流入経路軸** — `utm_source/medium/campaign`、`link_before_conversion`、`form_sender` 別の入会率。
   「CVは増えたが入会率が低い経路」を名指しで特定せよ。
2. **問い合わせ種別軸** — `inquiry_kbn` 別の入会率と構成比変化。
   構成比シフトだけで歩留まりが説明できるか検証（Simpsonのパラドックス確認）。
3. **相談所オペレーション軸** — 相談所別に、CV数増加とリードタイム・放置率
   （既読NULL率 / アクション0件率）の相関。キャパオーバー仮説をデータで肯定/否定せよ。
4. **アクション「量」と「質」軸** — 入会に至った見込み客の平均アクション回数・種別・初回接触までの時間 vs
   至らなかった見込み客。**どのアクションパターンが入会と最も相関するか**を示す。
5. **期待値ギャップ軸** — 流入時の希望（`consultation_method_kbn`、希望日時 `counseling_request1..3_ts`、エリア）と
   相談所側の実提供（`online_interview_kbn`、`physical_store_flag`、`charge_free_counseling_flag`、
   料金プラン、`available_area_ary`）の不一致。不一致ケースの入会率を一致ケースと比較せよ。
6. **システム未活用相談所軸** — CVを受け取っているのに
   `informations` 行 0件 / `agency_viewed_ts` 全NULL / `interview_management` 0件 の相談所を抽出。
   **その相談所群が全CVの何%を占め、入会率は他とどう違うのか。**
   （※データ上見えないだけで実際は独自Excel等で運用している可能性がある。断定せず「可視性欠損」として扱え）
7. **入会順調相談所の傾向軸（Positive Deviance）** — 入会率上位群と下位群を、CV数を揃えて比較。
   掲載プラン、料金設定、報酬設定、オンライン対応、スタッフ数、既読速度、アクション回数・種別、
   独自ステータス活用有無 などのどの変数が効いているのか。
   **「順調な相談所が必ずやっていて、不調な相談所がやっていないこと」を specific に言い切れ。**
