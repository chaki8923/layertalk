# LayerTalk 収益化・実装計画

- ステータス: Event Pass / Phase 1 implemented
- 作成日: 2026-08-15
- 対象: 発表者用macOSアプリ、観客用Web、Supabaseバックエンド
- 目的: LayerTalkの体験を壊さず、単発イベントから企業利用まで段階的に課金できる状態を作る

## 1. 結論

LayerTalkは観客ではなく、発表者・イベント主催者に課金する。

無料版では「コメント・スタンプ・質問が画面上に流れる」という中核体験を成立させる。有料版では、主催者が本番を安全に運営し、イベント後に成果を持ち帰り、自社ブランドで継続運用できるようにする。

参加人数を主な課金軸にはしない。競合の多くが人数制限を料金境界にしているため、LayerTalkは「観客数を気にせず使える」を価格体系そのものの差別化にする。

最初に販売する商品は、単発イベント向けの **Event Safe Pack** とする。

## 2. 収益化の原則

1. 観客は無料・匿名・アプリ不要のままにする。
2. 課金対象は発表者または主催組織とする。
3. 盛り上がる機能ではなく、安全運営・記録・ブランド・組織管理に課金する。
4. 発表開始直前や発表中に、決済を要求しない。
5. 購入確認の通信障害によって、本番が開始できない状態を作らない。
6. 緊急終了など最低限の安全機能は無料版にも残す。
7. 有料機能の権限はクライアントの表示だけでなく、サーバー側でも検証する。
8. 観客数に比例して請求する使用量課金は、初期スコープに入れない。

## 3. 料金仮説

価格は確定値ではなく、販売テスト用の初期仮説とする。最初の5〜10件は手動販売も許容し、支払い意思を確認してから固定する。

| プラン | 対象 | 価格案 | 権利 |
|---|---|---:|---|
| Free | 個人登壇、勉強会、試用 | 0円 | 中核体験、LayerTalkブランド付き、短期履歴 |
| Event Pass | 単発イベント | 2,980円／イベント | Safe Pack、出力、ブランド設定、30日履歴 |
| Pro | 登壇・研修を繰り返す個人 | 4,980円／月 または 29,800円／年 | Event Pass相当をイベント数無制限、履歴・プリセット |
| Team | 企業・コミュニティ | 9,800円／月〜 | 5発表者、共同運営、共有ブランド・プリセット |
| Enterprise | 社員総会、イベント会社 | 30万円／年〜 | SSO、監査、専用環境、SLA、導入支援 |

### Event Passの定義

- 1つのルームに紐づける。
- 購入時から7日間、または指定したイベント終了日時まで有効とする。
- 有効期間中に開始したプレゼンは、途中で期限を迎えても終了まで有料機能を維持する。
- 同じイベントのリハーサルと本番は、同じルームであれば追加購入を求めない。
- 別ルームへの権利移動は、未使用時に限るなど別途ルールを決める。

### 無料版のデータ保持

無料ルームのコメント履歴は7日を初期案とする。有料イベントは30日、Proは契約中または最大1年を初期案とする。

現在はルームとコメントが無期限に残り、Storageのカスタムスタンプ画像はルーム削除だけでは消えない。収益化前に、保持期限とStorageを含む削除ジョブを設計する必要がある。

## 5. 最優先で実装する有料価値

### 5.1 モデレーション

企業イベントで最大の導入障壁になっている「不適切な投稿を止められない」を解消する。

最初の範囲:

- コメントの個別非表示
- コメント表示の一時停止
- NGワードとの完全一致・部分一致
- 質問だけ表示するモード
- 0〜5秒の表示ディレイ
- 承認されたコメントだけ流すモード
- カスタムスタンプの一括無効化

緊急の「プレゼン終了」と「コメント／スタンプを画面から止める」は無料版にも残す。有料版は、イベントを継続したまま細かく制御できることに価値を置く。

### 5.2 発表レポート

イベント終了後に以下を生成する。

- 発表開始からの経過時間付きコメント一覧
- 質問一覧といいね数
- 未回答としてマークした質問
- 1分ごとのコメント数・スタンプ数
- 反応が最大だった時間帯
- CSV出力
- Markdown出力

初期版では自動要約を入れない。まず正確な時刻・件数・本文を持ち帰れることを優先する。

### 5.3 ブランド設定

- オーバーレイ上のLayerTalk表記を非表示
- 主催者ロゴ
- ブランドカラー
- QRカードのロゴ・色
- 表示スタイルの保存

## 6. 課金導線

### 発表前

- コントロール画面に「本番を安全に運営」カードを置く。
- 有料機能は内容を確認できるが、操作すると購入案内を開く。
- 「公開イベント」「社内イベント」などの用途選択から、Event Passを案内できるようにする。
- 発表開始ボタン自体は無料版でも押せるようにする。

### 発表中

- 新たな決済画面を出さない。
- 未購入機能を誤操作した場合は、小さな説明だけ表示し、プレゼン操作を邪魔しない。
- すでに開始したプレゼン中に権利が失効しても、終了までは機能を維持する。

### 発表後

- 終了画面に件数サマリーを無料で表示する。
- CSV／Markdown出力と詳細レポートを有料導線にする。
- Free利用者にも「このイベントでは質問がN件、反応ピークがM分時点」と価値の一部を見せる。

## 7. 目標アーキテクチャ

### 認証と所有権

観客は引き続き匿名とし、発表者だけSupabase Authで認証する。

初期の認証方式は、Tauriアプリ内で完結しやすいメールOTPを第一候補とする。外部ブラウザからアプリへ戻すOAuth／ディープリンクは初期実装では避ける。

必要な変更:

- `rooms.owner_id` を追加し、`auth.users.id` と紐づける。
- 新規ルーム作成は、認証済み発表者だけが呼べるRPCへ移す。
- ルーム設定、モデレーション、出力は所有者または共同運営者だけに許可する。
- 観客によるルーム参照、コメント、スタンプは匿名のまま維持する。
- 既存ルームは移行期間のみ「legacy free room」として扱うか、所有権を引き継ぐ導線を用意する。

公開前で既存ユーザー移行が不要なら、匿名ルーム作成を廃止し、既存開発ルームを整理する方が安全で実装も小さい。

### 権限モデル

UI上のロック表示だけを権限判定にしない。Supabase側で、発表者とルームに対する有効な権利を判定する。

想定テーブル:

| テーブル | 用途 |
|---|---|
| `presenter_profiles` | 発表者プロフィール、Stripe Customer ID |
| `room_members` | ルーム所有者・共同モデレーター |
| `entitlements` | プラン、対象ルーム、有効期間、状態 |
| `billing_events` | Webhookイベントの重複処理防止 |
| `presentation_sessions` | 開始・終了時刻、プランスナップショット |
| `moderation_rules` | NGワード、ディレイ、承認モード |
| `moderation_actions` | 非表示・承認などの監査記録 |

`entitlements` は少なくとも以下を持つ。

- `kind`: `event_pass | pro | team | enterprise | beta`
- `owner_id`
- `room_id`: Event Passだけ必須
- `starts_at`
- `expires_at`
- `status`: `active | grace | expired | revoked`
- `source`: `stripe | manual | promotion`
- Stripe側オブジェクトID

発表開始時に、有効な権利を `presentation_sessions.entitlement_snapshot` に保存する。これにより、セッション中の期限切れや一時的な通信断で機能が消えないようにする。

### コメント投稿とモデレーション

現在の匿名 `comments` INSERTをそのまま残すと、NGワードや承認状態をサーバー側で強制できない。モデレーション導入時は、直接INSERTを閉じて `post_comment()` RPCに移す。

想定するコメント状態:

- `approved`: 一覧とオーバーレイに表示
- `pending`: モデレーターだけが確認可能
- `hidden`: 観客一覧とオーバーレイから除外

`post_comment()` はルーム設定とNGワードを確認し、初期状態を決める。Realtime購読側も `approved` だけを通常表示し、発表者側には保留中の購読経路を追加する。

## 8. Stripe決済設計

単発購入とサブスクリプションの両方にStripe Checkout Sessionsを使う。独自のカード入力画面や、PaymentIntentsによる手動の定期更新処理は作らない。

### 商品構成

- Event Pass: Checkout Sessionの `mode: payment`
- Pro／Team: Checkout Sessionの `mode: subscription`
- プラン変更、解約、支払い方法変更: Stripe Customer Portal
- Enterprise: 当面は問い合わせ・請求書対応

### 実装ルール

- Stripe APIはサーバー側だけから呼ぶ。
- Tauriアプリや観客Webに秘密鍵を埋め込まない。
- 可能な限り最小権限のRestricted API Keyを使う。
- Checkout作成時に、認証済みの `owner_id` と対象 `room_id` をサーバー側で検証する。
- APIバージョン `2026-03-25.dahlia` 以降では、Checkout Sessionにランダムな8文字サフィックスを持つ `integration_identifier` を付ける。
- `payment_method_types` は指定せず、Stripe Dashboardの動的な支払い方法設定を使う。
- 税務登録を確認するまで `automatic_tax` を有効化しただけで対応済みとみなさない。

### Webhook

権限付与の正は、Checkoutの成功URLではなくStripe Webhookとする。

最低限処理するイベント:

- `checkout.session.completed`
- `customer.subscription.created`
- `customer.subscription.updated`
- `customer.subscription.deleted`
- `invoice.paid`
- `invoice.payment_failed`

Webhook署名を必ず検証する。`billing_events` にStripe Event IDを主キーとして保存し、同じイベントが再送されても権限を二重作成しない。

返金、チャージバック、支払い失敗時の失効方針は別途決める。少なくとも進行中のプレゼンは突然停止させず、次回開始時から制限する。

## 9. 実装フェーズ

### Phase 0: 販売仮説の検証

目的: 決済基盤を作る前に、2,980円の支払い意思を確認する。

- 有料機能の説明画面を作る。
- ロックされた機能のクリックを計測する。
- `beta` 権利を手動付与できるようにする。
- 5〜10件のイベントにEvent Safe Packを提案する。
- 購入理由、見送り理由、必要な参加人数、イベント種別を記録する。

完了条件:

- 少なくとも3件が実際に有料で利用する、または価格以外の明確な導入条件が得られる。

### Phase 1: 発表者認証とルーム所有権

- Supabase Authを導入する。
- `rooms.owner_id` とRLSを追加する。
- 認証済みルーム作成RPCを実装する。
- 発表者用アプリにログイン／ログアウトを追加する。
- 既存の匿名ルーム作成を閉じる。

完了条件:

- 観客はログインせず参加できる。
- 発表者Aが発表者Bの設定や履歴を変更できない。
- 未認証者が新しい発表ルームを作れない。

### Phase 2: Event Safe Pack

- コメント状態と `post_comment()` RPCを追加する。
- 個別非表示、承認、NGワード、表示ディレイを実装する。
- 入室パスコードを実装する。
- `entitlements` と機能判定を実装する。
- ローカルに権利確認結果と有効期限をキャッシュする。

完了条件:

- 未購入者がAPIを直接呼んでも有料設定を変更できない。
- 通信断でも、直前に確認済みの有料権利で本番を開始できる。
- セッション中に権利が切れても表示や操作が突然変わらない。

### Phase 3: 記録と出力

- `presentation_sessions` を追加する。
- 開始・終了とイベント時刻を保存する。
- CSV／Markdown出力を実装する。
- 発表後サマリーを表示する。
- 保持期限とStorage画像削除ジョブを実装する。

完了条件:

- コメント時刻が「発表開始から何分何秒」で正しく出る。
- 開始前のコメントが発表レポートに混入しない。
- 無料／有料の保持期限に従ってDB行とStorage画像が削除される。

### Phase 4: Stripe課金

- Checkout Session作成APIを実装する。
- Webhookと冪等処理を実装する。
- Event Pass購入とルーム紐づけを実装する。
- Pro／Teamサブスクリプションを実装する。
- Customer Portalを接続する。
- 返金・解約・支払い失敗を検証する。

完了条件:

- Checkout成功画面を偽装しても権限が付かない。
- Webhookの重複配信で権限が二重作成されない。
- 解約後も契約期間末までは利用できる。
- 失敗した請求の扱いが画面と権限で一致する。

### Phase 5: Team／Enterprise

- 共同モデレーター
- チーム共有ブランド・プリセット
- 席数管理
- 監査ログ
- SSO／SCIM
- 専用Supabaseまたはデータ保存地域の選択肢
- SLAと導入支援

個人・単発プランで支払い意思が確認できるまで着手しない。

## 12. リリース前の受け入れ条件

- 観客は課金・ログインなしで参加できる。
- 無料版でもプレゼンを開始・終了できる。
- 課金画面が発表中に強制表示されない。
- 権利確認APIが落ちても、確認済み権利には猶予がある。
- 有料権利の期限切れが進行中のプレゼンを壊さない。
- ルーム所有者以外はモデレーションや出力を実行できない。
- Stripe秘密鍵がTauri・ブラウザ・Git履歴に入らない。
- Webhook署名検証と冪等処理がある。
- 無料ルームのデータが保持期限後にStorageを含めて削除される。
- 本番相当のKeynote／PowerPoint重ね表示で一連の操作を実機確認する。

## 13. 初期スコープに入れないもの

- 観客への課金
- 投げ銭
- スタンプのマーケットプレイス
- 広告表示
- 観客数に応じた従量課金
- 投票・クイズ機能の競合追随
- AI要約
- 複雑なクーポン・紹介報酬
- 再販事業者向け請求

投げ銭はイベント自体のマネタイズ機能になり得るが、返金、不正利用、本人確認、配分、モデレーションの責任が増える。主催者向けSaaSの課金が成立してから検討する。
